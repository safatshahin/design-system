# How the Design System MCP works

A plain-language guide to the MCP server in this repository: what it
is, how it works, how AI tools use it, and what it would take to host
it on design.moodle.org.

## What problem it solves

AI coding assistants (Claude Code, OpenCode, Cursor, Copilot and
similar) are good at writing UI code but they do not know our design
system. Left alone they invent their own markup, hardcode colours and
spacing, and guess at component props. The MCP server fixes that by
giving the assistant a way to *ask*: "which component should I use
for this?", "what props does Button take?", "is there a token for
this colour?", "show me a working example".

MCP (Model Context Protocol) is simply the standard way AI tools talk
to a source of information. Our server speaks that standard, so any
MCP-capable tool can use it without custom integration.

## The three things it knows about

**Components.** Every component in `components/` (Button, Tooltip,
Checkbox, ...) with a one-line purpose ("when to use this"), its props
with types and descriptions, real example code from its Storybook
stories, the design tokens it uses, and where its files live.

**Design tokens.** Every `--mds-*` CSS variable (about 350 of them)
with its value and a category such as colors, spacing, typography,
borders or sizes.

**Design guidance.** The design team's written guidance from
design.moodle.com (ZeroHeight): usage decisions, foundations,
accessibility rationale, contribution rules. It lives in
`.github/instructions/*.instructions.md` (the big one is
auto-generated by `npm run build-docs`) and is far too large to hand
to an AI whole, so the server splits it into a few hundred small
sections that can be searched and fetched one at a time. Components
and tokens answer WHAT exists; the guidance answers WHY and WHEN.

## How it works, step by step

```
  AI tool (e.g. Claude Code)
        |
        |  starts the server as a background process and
        |  talks to it through that process's input/output
        v
  npm run mcp:serve  ->  scripts/mcp-server.ts  ->  src/mcp/index.ts
                                                          |
                                                   at startup, reads:
                                                          |
                    +-------------------------------------+------------------+
                    |                                     |                  |
          dist/component-index.json          components/*/*.tsx        tokens/css/*.css
          (name + purpose per component)     (props, stories, CSS)     (the token values)
```

1. **The AI tool starts the server itself.** There is no daemon and no
   port. When you open an AI session, the tool runs `npm run mcp:serve`
   in this checkout and keeps that process alive for the session. When
   the session ends, the server ends. This also means **a running
   session keeps the data it loaded at startup**: after you change
   code or rebuild, start a new session to see the changes.

2. **At startup the server reads everything into memory.** It loads
   the component index, opens each component's source, story and CSS
   file to extract props, examples and token usage, and parses the
   token CSS files. The whole design system is small (a handful of
   components, a few hundred tokens), so this takes well under a
   second and no database or search engine is needed.

3. **Each question becomes a tool call.** The AI picks one of the
   tools below, the server answers from memory in JSON, and the AI
   uses the answer to write correct code.

### The files that make up the server

| File | What it does |
|---|---|
| `scripts/mcp-server.ts` | The command-line entry point. `npm run mcp:serve` runs this; it takes an optional `--path` to the design-system checkout (defaults to the current directory) and starts the server. |
| `scripts/mcp-smoke-test.ts` | A quick self-check (`npm run mcp:test`): starts the server, calls a few tools, and confirms real data comes back. Run it after building to make sure everything is wired up. |
| `src/mcp/index.ts` | The server itself. Registers the tools with the MCP library, receives each tool call, and routes it to the right handler. |
| `src/mcp/indexer.ts` | The data layer. At startup it reads the component index, the component source files and the token CSS, and builds the in-memory catalogue. All searching and lookups (components, tokens, categories, near-miss suggestions) live here. |
| `src/mcp/tools/components.ts` | Defines the six component tools (what they are called, what inputs they take) and produces their answers. |
| `src/mcp/tools/tokens.ts` | Defines the five token tools and produces their answers, including the "no tokens loaded" guidance. |
| `src/mcp/tools/guidelines.ts` | Defines the two design-guidance tools (search a section, fetch a section) over the `.github/instructions/` documents. |
| `src/mcp/types.ts` | The shared data shapes: what a component record, a prop, a token, and the index status look like. |

Rule of thumb when changing things: a new tool touches `tools/*.ts`
(definition plus handler) and `index.ts` (the name registry); a change
in how data is read or searched touches `indexer.ts`; a change in what
a record contains touches `types.ts`.

### Where the data comes from

| Data | Read from | Produced by |
|---|---|---|
| Component list and purposes | `dist/component-index.json` | `npm run build-component-index` |
| Props, examples, token usage | the component's `.tsx`, `.stories.tsx` and `.css` files, read live | nothing to build |
| Tokens | `dist/tokens/css/*.css`, or `tokens/css/*.css` if `dist/` has no tokens | `npm run build-tokens` |
| Design guidance | `.github/instructions/*.instructions.md` | committed; the large one regenerates from ZeroHeight via `npm run build-docs` (needs `ZEROHEIGHT_MCP_URL`) |

So the only setup needed for full data is:

```bash
npm install
npm run build-tokens
npm run build-component-index
```

A full `vite build` is not required.

Two details worth knowing about tokens: the CSS **filename** is the
theme (`light.css` today, `dark.css` in future), and the token's
**category** (colors, spacing, ...) comes from the token's own name,
so `--mds-color-primary` is a colour and `--mds-spacing-md` is
spacing. Every token carries both.

## The tools the AI can call

Component tools:

| Tool | What it answers |
|---|---|
| `list_components` | "What components exist?" - every component with its purpose. The cheapest overview. |
| `search_components` | "Is there something for X?" - ranked search by name, keyword, category or token. `*` returns everything. |
| `get_component_api` | "How do I use Button?" - purpose, props with types and descriptions, tokens used, file paths. |
| `get_component_example` | "Show me working code" - the real Storybook story source, one per story. |
| `check_component_accessibility` | Accessibility hints found in the source (clearly marked as hints, not an audit). |
| `find_components_using_token` | "If I change this token, what is affected?" |

Token tools:

| Tool | What it answers |
|---|---|
| `list_token_categories` | "What kinds of tokens exist, and how many?" Also reports where tokens were loaded from. |
| `search_tokens` | "Is there a token for this?" - ranked search, optional category filter, `*` for everything. |
| `get_token_value` | "What is `--mds-spacing-md`?" |
| `get_tokens_by_category` | "Show me all the spacing tokens." |
| `validate_token_usage` | "How should I use this token?" - a CSS snippet plus best practice for its category. |

Design-guidance tools:

| Tool | What it answers |
|---|---|
| `search_guidelines` | "What does the design team say about X?" - ranked search over the guidance sections, each result carrying an id and a snippet. |
| `get_guideline` | Fetch one guidance section by id - the full text of just that section. |

A note on section names: the generated guidance names its sections by
breadcrumb ("Button > Design > States"). Older generated files lack
the page name in that breadcrumb ("Design > States") - regenerating
with `npm run build-docs` fixes it, because the generator now stamps
each page's title into the file.

### Rules the tools follow

These came from watching AI tools use the server, and they matter as
much as the data:

- **Answers are kept small.** Searches are ranked and capped; lists
  say how many more there are. An AI has a limited "working memory",
  so a 90KB dump of every token is worse than 25 relevant ones.
- **A failed lookup says what to try next.** Ask for a token that does
  not exist and you get the closest names and the category list. Ask
  for an unknown component and you get the component names.
- **Broken data is never hidden.** If the tokens were not built, every
  token tool says exactly that and names the command to run. Every
  listing includes a one-line status ("17 components, 354 tokens,
  indexed at ...") so a stale or partial build is visible.

## How to connect an AI tool

Point the tool at this checkout (after the build steps above):

```bash
# Claude Code
claude mcp add design-system -- npm run --silent mcp:serve --prefix /path/to/design-system

# OpenCode: add a "local" MCP entry that runs `npm run mcp:serve` in the checkout
```

A typical session then looks like: the AI calls `list_components` to
see what exists, `get_component_api` for the props of the one it
picks, `get_component_example` for working code, and `search_tokens`
while writing CSS so values come from tokens instead of being typed in
by hand.

The Moodle review tooling (`moodle-dev`) treats these lookups as
mandatory for any change that touches UI: a review flags hardcoded
values where a matching token exists and hand-rolled markup where a
component exists, citing what the tools returned.

## Hosting it on design.moodle.org

Today every user needs a local checkout, Node, and the build steps.
Hosting the server on design.moodle.org would remove all of that: an
AI tool would connect to a URL and always see the current, published
design system. What it takes:

1. **Serve it over HTTP.** The server currently talks over a process's
   input/output (stdio). The MCP library it uses also supports plain
   HTTP; adding that is a small change (roughly 50 lines of wiring)
   and none of the tools change. It would live at
   `https://design.moodle.org/mcp`.
2. **Build the data in the site's pipeline.** The token CSS and the
   component index are already build outputs; produce them in the same
   CI job that publishes the site and restart the server on deploy.
   Then what the server answers always matches what the site shows,
   and the "stale local checkout" problem disappears entirely.
3. **Start read-only and open.** The tools change nothing and the data
   is the public design system, so no login is needed to begin with.
   Rate-limit it like any public endpoint; per-team API keys can be
   added at the proxy later if usage tracking is wanted.
4. **Handle versions with a parameter, not separate URLs.** If the
   site ever serves more than one design-system version, add a
   `version` parameter to the tools (the Moodle docs MCP does this per
   Moodle version). AI tools cope with parameters far better than with
   discovering alternative URLs.
5. **Connecting becomes one line, with nothing to install:**
   `claude mcp add --transport http design-system https://design.moodle.org/mcp`.

Until then, the local server is the way to run it, and remember to
rebuild the data and start a new AI session after pulling changes.
